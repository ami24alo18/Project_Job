# Job Application Agent

## Phase 5 verified application-package drafts

Phase 5 turns a completed Phase 4 evaluation into a revisioned **draft** application package with fact-grounded resume content, a cover letter, recruiter-message and application-answer drafts, claim evidence, and deterministic HTML, PDF, and DOCX resume artifacts. Every candidate claim must cite an eligible verified fact from the exact immutable profile version. Unsupported requirements remain warnings instead of becoming candidate skills, and sensitive questions remain unanswered.

Artifacts are rendered server-side from validated structured content, checksummed, stored in the existing private MinIO bucket, and downloaded only through authenticated backend endpoints. Contact details are injected during deterministic rendering and are not sent to the model. Regeneration creates another historical revision and does not silently overwrite user edits.

All Phase 5 packages are labelled **Draft — not approved or submitted**. This phase does not approve, submit, browse, log in, fill forms, solve CAPTCHAs, or send messages/emails. AI content generation and n8n package automation are disabled by default. See the [Phase 5 guide](docs/phase-5-verified-application-packages.md) and [ADR-005](docs/architecture/ADR-005-verified-application-content-and-deterministic-document-generation.md).

## Phase 4 matching

Phase 4 introduces deterministic filtering before any optional AI request. It evaluates immutable published profile snapshots, stores stable rule reason codes and safe evidence, normalizes available score weights on the server, derives recommendations from configurable thresholds, and retains historical evaluations and human feedback. Identical rule inputs are cached. AI is disabled by default.

Configure AI only in the backend environment with `AI_EVALUATION_ENABLED`, `OPENAI_API_KEY`, `OPENAI_MODEL`, request/token/input/batch limits, timeout, and concurrency limits. The key must never be placed in React or n8n. Prompt `job-evaluation/v1` and its strict JSON schema are immutable classpath resources with SHA-256 checksums. The OpenAI adapter uses the Responses API, structured output generated by the official Java SDK, `store: false`, and supplies no tools.

Default weights are Skills 35, Experience 20, Role 15, Location 15, Domain 10, and Compensation 5. Recommendations use 85/75/60 boundaries; unavailable dimensions are omitted and remaining weights are proportionally normalized with `HALF_UP` integer rounding. Deterministic hard failures always produce `SKIP`, while insufficient or low-confidence data requires human review.

A self-hosted, human-controlled job application workspace. Phase 2 provides candidate data, a verified resume fact bank, private master-resume storage, reusable answers, and immutable published profile versions. Phase 3 adds authorized public-feed, structured email-alert, and manual job ingestion with normalization, deterministic deduplication, and auditable source runs. It does not scrape websites, call an LLM, match or score candidates, generate application material, or submit applications.

## Architecture and scope

The backend is a Java 21 Spring Boot modular monolith backed by PostgreSQL and Flyway. React, TypeScript, Vite, Material UI, React Router, and Axios provide the UI. Resume and generated application artifacts are private MinIO objects while searchable metadata, extracted resume text, normalized jobs, source configurations, source-run history, application-package revisions, structured generated content, and claim provenance live in PostgreSQL. Self-hosted n8n owns bounded scheduling/orchestration; remote provider access remains behind backend adapters.

See [ADR-001](docs/architecture/ADR-001-modular-monolith.md), [ADR-002](docs/architecture/ADR-002-verified-resume-fact-bank.md), [ADR-003](docs/architecture/ADR-003-authorized-job-ingestion.md), [ADR-004](docs/architecture/ADR-004-explainable-ai-job-matching.md), [ADR-005](docs/architecture/ADR-005-verified-application-content-and-deterministic-document-generation.md), the [Phase 1 report](docs/phase-1-foundation.md), the [Phase 2 report](docs/phase-2-candidate-profile.md), the [Phase 3 report](docs/phase-3-job-ingestion.md), the [Phase 4 report](docs/phase-4-ai-job-matching.md), and the [Phase 5 guide](docs/phase-5-verified-application-packages.md).

## Phase 2 workflow

1. Sign in using the environment-backed application credentials.
2. Create the core profile at `/profile`.
3. Configure target titles, locations, skills, exclusions, thresholds, and daily limits at `/preferences`.
4. Upload a genuine PDF or DOCX at `/resume-documents`, review extracted plain text, and activate one master resume.
5. Create facts manually or import structured JSON at `/resume-facts`. Imports always remain `DRAFT`.
6. Review and explicitly verify supported facts. Editing a verified fact resets it to `DRAFT`; rejected or archived facts must be restored before use.
7. Add common answers at `/reusable-answers`. Compensation, demographic, and legal answers cannot be safe for autofill; work-authorization and relocation answers default to review.
8. Publish at `/profile/versions`. Publication requires valid preferences, an active resume, and at least one verified fact. Identical content reuses the latest immutable version.

Future automation must consume an active published version, not mutable draft tables. Extracted resume text never becomes a fact automatically.

## Phase 3 job ingestion

### Supported sources and configuration

| Source | Configuration | Region | Backend network behavior |
| --- | --- | --- | --- |
| Manual | No source configuration | Not applicable | Validates links as data and never fetches them |
| Lever | Public Lever site/company identifier | `GLOBAL` or `EU` | GETs the documented public Postings API only |
| Greenhouse | Public job-board token | `DEFAULT` | GETs the documented public Job Board API only |
| Email webhook | Logical alert source name | `DEFAULT` | Receives approved structured fields from n8n; fetches no links |

Create and manage sources at `/job-sources`. A source contains a display name, source type, provider identifier, supported region, page/run limits, missing-run threshold, and enabled state. Lever uses the site identifier from its hosted postings feed; choose `GLOBAL` for `api.lever.co` or `EU` for `api.eu.lever.co`. Greenhouse uses the board token found in the organization's public job-board URL, not a Harvest API key or employer credential. Because a public feed may omit a company field, the backend uses the source display name as that source's fallback normalized company; choose a stable employer name rather than an operational nickname. Email sources use the logical name that n8n sends as `sourceName`; matching trims surrounding whitespace and is case-insensitive.

Source configuration never accepts a base URL, scheme, host, path, header, credential, or executable request data. The backend selects fixed official HTTPS hosts from source type and region. Duplicate active type/identifier/region combinations are rejected, and archived configurations remain as history instead of being deleted.

### Manual entry

Use `/jobs/new` or `POST /api/v1/jobs/manual`. Company and title are required, together with at least one of a plain-text description or application URL. Manual application/source URLs must be valid HTTP(S) values but are never requested by the backend. The browser supplies an `Idempotency-Key` and reuses it for an ambiguous retry; API clients may supply the same optional header to receive the original result instead of creating another job.

Manual and provider jobs pass through the same normalization, URL canonicalization, hashing, and exact duplicate checks. Missing or syntactically invalid optional structured values remain unspecified rather than being guessed from description prose. A malformed required identity, URL, or salary range fails that individual record safely.

### Synchronization and source runs

An authenticated user can queue one source from `/job-sources` or `POST /api/v1/job-sources/{sourceId}/sync`. `POST /api/v1/job-sources/sync-enabled` considers every enabled Lever and Greenhouse source and is intended for n8n. A successful per-source request returns `202 Accepted` with its durable run identifier; an overlapping per-source request returns `409 Conflict`. The bulk endpoint returns `202 Accepted` with one entry per enabled source, reusing the current run identifier and status when that source already has an active run. Spring uses a bounded executor and does not run an internal schedule.

Inspect runs at `/job-source-runs`. Runs progress through `QUEUED`, `RUNNING`, and a terminal `SUCCEEDED`, `PARTIAL_SUCCESS`, or `FAILED` state and record discovered, created, updated, unchanged, duplicate, failed, and removed counts plus safe diagnostics. Provider calls occur outside database transactions. Run/source diagnostic context is propagated to worker threads so operational logs can be correlated without logging descriptions or raw responses. Only safe GETs may use bounded retry/backoff; permanent `4xx` responses other than `429` are not retried.

Only a complete successful source snapshot advances a missing-job count. Failed, partial, truncated, or page-limit-exhausted runs cannot mark a posting removed. After the configured number of complete successful runs omit a job, it becomes `SOURCE_REMOVED`; reappearance resets the counter and restores it unless it was manually archived. A job becomes `EXPIRED` only from a trusted structured expiry date or an explicit user action, never merely because it is old.

### Deterministic updates and deduplication

Deduplication is exact and auditable:

1. `(sourceId, externalId)` is provider identity. Repeated content updates the existing job or records `UNCHANGED`; it never creates another provider record.
2. A new record with the same canonical application URL is retained as `DUPLICATE` and points to the original job.
3. A SHA-256 fingerprint of normalized company, title, location, and canonical application host/path detects another exact cross-source duplicate.

Known tracking parameters such as `utm_*` do not create a new URL identity, while potentially identifying query parameters are preserved. Similar titles or employers alone are not enough to merge jobs. Provider refreshes do not overwrite manual corrections; an upstream change is exposed for review.

### Content and request safety

Job descriptions, provider fields, and email-mapped values are untrusted. HTML is parsed into bounded plain text; scripts, styles, markup, unsafe control characters, and excess content are removed before persistence. React renders only normalized text and opens a validated external application link through an explicit user action in a separate tab. Complete descriptions and raw provider/email payloads are excluded from audit metadata and logs.

Provider endpoints are derived from a strict Lever/Greenhouse allowlist. Source configuration cannot select an arbitrary URL, IP address, local-network target, redirect host, `file:`, or `ftp:` destination. Links found in jobs, manual submissions, or email alerts are stored as data and never fetched. The connectors use no private employer API keys and never call an application-submission endpoint.

## Phase 5 draft workflow

1. Complete a Phase 4 evaluation for an active job and publish/retain the exact immutable profile version used by that evaluation.
2. From the job/evaluation action or `/application-packages`, request a package. The backend accepts an `Idempotency-Key`; reuse it after an ambiguous timeout.
3. Follow the returned `Location`. The bounded generation call currently returns its `202` response after generation finishes, although concurrent readers may observe `REQUESTED` or `GENERATING`. Reuse the same idempotency key after an ambiguous disconnect. A `READY` package is still a draft.
4. Inspect structured resume content, cover letter, recruiter-message and question drafts, unsupported requirements, warnings, and the evidence/provenance view.
5. Download HTML, PDF, or DOCX only through the authenticated application endpoints. MinIO keys and credentials are never returned.
6. Regenerate explicitly to create a new revision. User-edited content is visibly marked and is not silently replaced.

The package APIs are documented in the running Swagger UI and summarized in the [Phase 5 guide](docs/phase-5-verified-application-packages.md#rest-api). Generated questions are classified as `VERIFIED_AUTOMATIC`, `SUGGESTED_REQUIRES_REVIEW`, `USER_INPUT_REQUIRED`, or `SENSITIVE_NEVER_AUTOMATIC`; sensitive questions and missing current decisions remain unanswered.

The existing `MINIO_BUCKET` stores master resumes and generated artifacts privately. For local setup, start PostgreSQL and MinIO before the backend. The backend creates storage objects through its private adapter; do not configure anonymous bucket access or use the MinIO console URL as an application download link. Back up PostgreSQL and MinIO together.

## n8n connectivity

Follow [the Phase 1 workflow instructions](automation/n8n-workflows/README.md). From the host, the equivalent check is:

```bash
curl -X POST http://localhost:8080/api/v1/system/n8n/ping -H "X-N8N-WEBHOOK-SECRET: your-value-from-env"
```

The response must contain `"status":"ACKNOWLEDGED"`. Never commit the real secret or place it directly in an exported workflow.

For scheduled source synchronization, follow the [Phase 3 scheduled-sync guide](automation/n8n-workflows/phase-3-scheduled-sync.md): create an n8n HTTP Basic Auth credential, schedule `POST http://backend:8080/api/v1/job-sources/sync-enabled`, split the returned run IDs, and poll their authenticated run endpoints with a visible finite attempt count. Successful runs finish silently; only failed, partial, malformed, or timed-out branches should notify. Credentials belong in n8n credentials, never in nodes or exports.

For email alerts, first create an enabled `EMAIL_WEBHOOK` source, then follow the [structured email-mapping guide](automation/n8n-workflows/phase-3-email-alert-mapping.md). Keep mailbox credentials in n8n, accept only a known sender/template, project immediately to the stable message ID and approved job fields, and send them to `POST http://backend:8080/api/v1/job-sources/email-alert/events` with `X-N8N-WEBHOOK-SECRET`. Configure n8n execution-data saving and pruning so a temporary trigger body is not retained longer than explicitly required. Replays must retain the same provider `messageId`; they return the stored acknowledgement with `replayed=true`. A valid event with one or more invalid jobs returns `PARTIAL_SUCCESS` and safe per-job results. Do not forward a complete email body, attachments, unrelated content, or application-page data.

The Phase 3 assets are construction guides, not claimed importable JSON exports. If an operator later exports a workflow, inspect it for credentials/personal content and validate re-import against the installed n8n version before treating it as portable.

For Phase 5, import the version-controlled [eligible application-package workflow](automation/n8n-workflows/phase-5-eligible-application-package.json) and follow its [credential, event, retry, retention, and validation guide](automation/n8n-workflows/phase-5-application-package-setup.md). It receives only evaluation/job UUIDs, verifies the authoritative evaluation, submits that `evaluationId` to the authenticated package endpoint with a stable idempotency key and `X-N8N-Automation: true`, and makes at most three POST attempts. The marker causes the backend to enforce its stricter automation policy. The workflow retries only transport/backend `5xx` failures and stops immediately on authentication, validation, quota/policy, conflict, and other `4xx` responses. Completed success, error, and manual execution payload saving is disabled so n8n does not retain the full package response. It never approves, submits, fills a form, or sends anything externally.

## Backups and recovery

Back up PostgreSQL and MinIO together so database storage keys and resume objects represent the same point in time. Test restoration regularly and protect backups as sensitive personal data.

```bash
docker compose exec -T postgres pg_dump -U job_agent -d job_agent > job_agent-backup.sql
mc alias set job-agent http://localhost:9000 YOUR_MINIO_USER YOUR_MINIO_PASSWORD
mc mirror job-agent/job-agent-documents ./job-agent-documents-backup
```

For restoration, restore PostgreSQL into an empty compatible database and mirror objects back into the configured private bucket before starting the backend. n8n has separate database/configuration backup needs. Volume snapshots are also suitable when the container runtime can take coordinated snapshots. Never use `docker compose down -v` as part of a backup or upgrade.

## Troubleshooting and data safety

- A `401` from a Phase 2 endpoint means credentials are absent or invalid; sign in again after refreshing the frontend.
- A `401` from a job/source/run endpoint means Basic credentials are absent or invalid; n8n scheduled synchronization needs its configured backend Basic-auth credential.
- A `401`/`403` from the email-event endpoint means `X-N8N-WEBHOOK-SECRET` is missing or does not match the backend environment.
- A `400` while saving a source usually means the provider identifier/region is invalid; enter a Lever site, Greenhouse board token, or logical email source name, never a URL.
- A `409` normally means a stale record version, duplicate active source, repeated unique value, or synchronization already running. Reload before retrying an edit; inspect the current run before queuing another.
- A `429`, timeout, or provider `5xx` is recorded as a safe run failure/partial result after bounded retries. Do not bypass the allowlist or repeatedly trigger the source.
- A `PARTIAL_SUCCESS` run may retain valid jobs but intentionally does not advance missing-job removal counts.
- If expected jobs become `SOURCE_REMOVED`, verify that the configured threshold was reached through complete successful runs; failed runs are not counted.
- If an email event returns `404`, confirm `sourceName`, after trimming and case-insensitive comparison, matches an enabled `EMAIL_WEBHOOK` source. Reuse the original `messageId` for a safe retry; a successful replay is a `200` acknowledgement with `replayed=true`, not a conflict.
- A `422` on publish identifies missing readiness fields in `fieldErrors`.
- A `503` during upload/download means MinIO is unavailable; the API does not expose its endpoint, credentials, or storage key.
- A Phase 5 `400` means package eligibility, immutable-source, automation-enable, daily-quota, question-policy, fact-reference, claim, or artifact validation failed. Inspect the safe problem detail and correct the source or configuration; do not relax provenance checks or retry a policy rejection rapidly.
- If content generation reports that the provider is disabled or credentials are missing, either keep the mocked/default path or configure `OPENAI_API_KEY` in the backend and explicitly enable `OPENAI_CONTENT_GENERATION_ENABLED`; never expose the key to the browser or workflow.
- A `STALE` application package preserves its historical revision. Review the stated source/version change and create an explicit regeneration rather than editing provenance.
- A missing/corrupt artifact must be regenerated through the backend after MinIO is healthy. Do not make the bucket public or return a storage key as a workaround.
- An n8n webhook acknowledgement only confirms that n8n accepted the event. During a controlled manual run, inspect the transient safe terminal result; for activated runs, inspect the durable package status because completed execution payloads are not retained. Retry with the same event/idempotency identity after an ambiguous failure.
- If n8n cannot ping the backend, use `backend:8080`, not `localhost:8080`, inside its container and confirm both services receive the same secret.
- PostgreSQL initialization scripts only run on an empty volume. Do not delete volumes merely to rerun them.

`docker compose down` stops services while preserving named volumes. `docker compose down -v` permanently removes PostgreSQL, MinIO, and n8n data and should only be used for an intentional, backed-up reset.
